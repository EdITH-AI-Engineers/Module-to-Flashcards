# Prompt Reduction and Cluster Batching Design

## Purpose and success criteria

The user wants faster validated flashcard generation on a separate computer with an RTX 3060 12 GB, currently observed at about two five-card clusters per minute and aiming for four. This coding laptop cannot establish that GPU throughput. The immediate work is to reduce repeated prompt input and avoid truncated or over-context responses without changing the exported 100-card module contract. The user accepts a small quality trade-off; the supplied task defines that as no more than a two-percentage-point drop in first-attempt validation pass rate and no increase in total retries. A five-cluster call is an experiment, not a promised speedup or a new default.

The canonical card remains an eleven-field `FlashcardDraft`, including the exact key `expalanation`. A module remains 20 clusters of five cards, validated together and written as two 50-card CSVs. The existing semantic checks for source grounding, answer leakage, plausible distractors, provenance wording, declarative true-false statements, and distinct questions remain in force. No new dependency is required.

## Approaches considered

1. **Measure, then reduce prompt overhead and retries; test batching behind an option (selected).** This separates input-token savings from output-generation cost. It can detect whether one larger call actually increases validated clusters per minute without putting all runs at risk of truncation.
2. **Make a five-cluster call the default immediately.** One prompt would avoid repeated prefill, but a 25-card response is much longer than today's five-card response. It could exceed the 12,288-token context, and one malformed response would waste or require repairing more work. No measurement currently supports this default.
3. **Only increase `n_ctx`.** A larger context might fit a 25-card response but also consumes more GPU memory per model context and may reduce the number of concurrent workers. It does not accelerate output-token generation by itself.

## Fixed benchmark and evidence

Stage 0 adds structured per-call metrics and a repeatable benchmark runner. `LocalQwenBackend.complete` accepts an optional task label (`concept_plan`, `cluster`, `retry`, `grounding_review`, `duplicate_review`, or `duplicate_repair`) and records prompt tokens, completion tokens, maximum tokens, finish reason, elapsed time, and exceptions without logging card text in the metrics file. The pipeline records each attempt's validation outcome and completed valid clusters. Existing completion and context exceptions keep their current meaning.

The benchmark runs the flashcard path from a fixed graph to the fully validated split CSV pair, with the same three input modules, model file, seeds, context, worker setting, review setting, and module order at every stage. It uses fresh output and course-corpus locations so reuse and previous runs cannot affect results. The three available TXT samples are the only supplied candidate corpus. Stage 0 prepares their graph inputs once, verifies that each can support a valid 20-concept baseline, and records content hashes; it does not commit the sample text or derived facts. The previously suggested CS0033 files are not suitable: current inspection found them unchecked with only 9–14 facts each. If any sample cannot yield a valid baseline, the benchmark stops and asks for a replacement rather than silently substituting data.

`benchmarks/baseline.json` and `benchmarks/after_stageN.json` record per-task mean and p95 prompt/completion tokens, length finishes, context errors, retry counts, first-attempt pass rate, valid clusters per minute, run settings, and input hashes. A root `REPORT.md` summarizes deltas, reversions, limitations of the small sample, and the hard no-think recommendation. The CPU laptop can establish token and quality comparisons; only a run on the separate RTX 3060 can confirm four valid clusters per minute or justify a GPU batching default. The runner accepts the same frozen inputs on that computer.

## Prompt and schema stages

Stage 1 uses compact JSON, repairs the identification-rule mojibake, removes only truly unused prompt-building work, drops slide provenance from concept-plan payloads, and replaces UUIDs in review prompts with short indices mapped back to canonical UUIDs in Python. Grounding review sends only fields needed to judge the card and its backing facts. Existing public prompt-builder arguments remain accepted. In particular, `_card_subject` and `_dedup_fingerprint` are currently called by `flashcard_pipeline.py`, but their computed `prior_signals` are discarded by `_cluster_payload`; remove that redundant computation before deleting the helpers.

Stage 2 splits the long shared system text into stable per-task prompts. Each card-type rule appears once in its authoritative system prompt, with at most eight short reminder lines near the end of a generation request. Task-specific facts and errors remain in the user message. Remove instructions made redundant by reliable schema enforcement only after observing the stage's first-attempt pass rate. Restore a reduction for a task if its pass rate falls by more than two percentage points versus baseline.

Stage 3 keeps strict schema-enforced structure with exact key spellings, allowed type and assessment-approach enums, and exact item counts. Where the grammar supports per-type card variants, the model may omit structural constants such as empty wrong options and non-true-false `is_true`. The parser fills those constants before constructing `FlashcardDraft` and before validation, so validators and CSV output still see the full eleven-field object. The existing `oneOf` concept-plan refusal remains. Chunked concept planning is added only if the baseline demonstrates plan truncation or context failure; merged chunks must still yield 20 unique, supported concepts.

## Backend and retry stages

Stage 4 adds a preflight `count_prompt_tokens(system, user) + max_tokens` check for every model call against the configured context and a safety margin. Calls trim whole optional payload entries or reduce their completion budget only to a task-specific floor; they never silently discard a concept's required grounding facts. If a call still cannot fit, it fails clearly or splits an eligible task. Completion truncation is never sent to a JSON parser. One retry may use additional headroom or a smaller task. Completion caps are based on measured p95 output size plus 50 percent, not a single large universal cap.

The hard no-think ChatML path is optional and off by default. It uses a schema-derived llama.cpp grammar, the same rendered bytes for token counting and completion, and an explicit end-of-message stop. Optional sampling controls retain today's defaults; a documented Qwen non-thinking preset is benchmarked separately. Neither path becomes default unless the benchmark improves or preserves validation quality. Hidden-reasoning evidence is reported rather than assumed.

Stage 5 makes retry prompts self-contained. It keeps rejected material as valid, whole JSON objects or explicitly labels a non-JSON summary instead of slicing characters. A cluster retry may request only flagged numbered cards; Python splices replacements into the original five-card tuple and proves unflagged cards unchanged. Unknown card locations fall back to a full-cluster retry. The existing grounding review already runs in groups of four, satisfying the requested three-to-five grouping; preserve it. The global LLM duplicate review stays unless a deterministic replacement proves parity: the local `are_near_duplicates` deliberately excludes one-word substitutions, while the current review instruction can consider filler or synonym substitutions. A hand-built parity set must expose that difference before any removal decision.

## Optional cluster batching experiment

After the prompt and truncation stages pass, a separate experimental setting requests 1, 2, or 5 concepts per model call on the same fixed corpus. The response schema preserves concept boundaries and five cards per concept. Each returned cluster is parsed and validated independently; only failed clusters are retried, and a truncated batch falls back to smaller calls without parsing partial JSON. The benchmark compares *validated* clusters per minute, first-attempt per-cluster pass rate, retries, context failures, and length finishes with worker count and context fixed. Batch size one remains the default until RTX 3060 results show a better setting that meets the quality and truncation gates. Increasing `n_ctx` is measured as a separate variable because its VRAM cost can change automatic worker count.

## Stage gates and delivery

Each stage starts with failing tests for its new behavior, then runs focused tests, the full suite, and the same three-module benchmark before a separate commit. The commit message includes its benchmark delta. A stage with a lower pass rate beyond the agreed two-point tolerance is reverted or narrowed before committing. Final acceptance requires at least 40 percent lower mean cluster-call prompt tokens and 25 percent lower overall mean prompt tokens than baseline, zero length finishes and context errors on the fixed benchmark, no more than a two-point first-attempt pass-rate drop, and no higher total retry count. If the available modules or hardware cannot establish a metric, the report marks it unverified rather than claiming success. The work remains on the new `clusters` branch, separate from the prior GPU-worker and split-CSV commits.
